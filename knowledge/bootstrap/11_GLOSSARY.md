# Forge Glossary

## Purpose and authority

This is the canonical vocabulary for the completed Bootstrap Knowledge
Package. It reconciles terminology already established in the preceding
chapters; it does not establish a new architecture, capability, or delivery
commitment.

| Term | Definition |
| --- | --- |
| **Workspace** | The highest product boundary: it owns product identity, architecture, roadmap, capabilities, governance, and the context for engineering history. It is not a repository or repository operator. |
| **Repository** | A version-controlled engineering asset belonging to a Workspace and the authoritative source of repository reality and repository evidence. |
| **Repository Catalog** | The Workspace-owned declarative mapping from repository identities to catalog roles, with exactly one canonical entry. |
| **Canonical Repository** | The single Repository Catalog entry that is the Workspace's primary product source of truth; it is not the Workspace and need not contain all implementation. |
| **Capability** | An explicit, versioned, discoverable, and bounded unit through which Forge may add engineering behavior; declaration alone is not implementation or approval. |
| **Knowledge Source** | A versioned, read-only external evidence provider used to inform Forge knowledge without being mutated or absorbed as authority automatically. |
| **Knowledge Package** | A bounded collection of bootstrap or domain knowledge that informs capture and reconciliation; it is not itself the final canonical repository record. |
| **Knowledge Distillation** | The future conceptual boundary that identifies reusable Knowledge Candidates from working material while retaining source and uncertainty. |
| **Knowledge Reconciliation** | The future conceptual boundary that compares a Knowledge Candidate with Repository Context and architectural constraints before a human-governed repository knowledge decision. |
| **Engineering Intent** | The canonical, model-independent record of one bounded engineering objective, rationale, scope, constraints, validation, and expected evidence. |
| **Proposal** | A bounded recommendation that scopes and justifies possible engineering work before it becomes an approved Engineering Intent. |
| **Runtime Provider** | A replaceable boundary that may translate an approved Engineering Intent into a runtime-specific representation without owning the intent or approval. |
| **Runtime Prompt** | A temporary, provider-specific execution artifact derived from Engineering Intent; it is never the canonical definition of work. |
| **Execution Host** | A replaceable environment that may perform bounded work but does not own engineering knowledge, governance, or completion decisions. |
| **Execution Mode** | The declared manner in which a Workspace approaches execution; it provides context and does not itself authorize work. |
| **Governance Profile** | The Workspace-selected declaration of human authority, review, and approval expectations for an execution context. |
| **Workspace Readiness** | The evidence-based assessment of whether a Workspace satisfies the declared prerequisites for an execution profile; it is distinct from Phase Completion. |
| **Phase Completion** | The evidence-first assessment that declared phase criteria are satisfied; implementation success or a status claim alone cannot complete a phase. |
| **Architecture Drift** | The assessed difference between Engineering Intent and Repository Reality; it is not determined by a prompt or runtime claim. |
| **Evidence** | Reproducible, assessable references used to evaluate declared outcomes against repository reality and other stated criteria. |
| **Repository Truth** | The authoritative account of repository reality established by observable repository evidence, which outranks conversations, reports, and runtime output for that reality. |
| **Architecture Handbook** | The future maintained architectural expression derived from reconciled Repository Knowledge; its authoring remains a next activity, not a completed capability. |
| **Product Identity** | The Workspace-owned understanding of what product is being engineered, distinct from repository identity and implementation topology. |
| **Bootstrap** | The temporary founding period in which Forge established and captured its Foundation knowledge before Forge-owned runtime execution exists. |
| **Genesis** | The bootstrap execution profile for bounded local transactions on the temporary host; it is not a permanent host or governance replacement. |
| **Managed** | An established execution-mode concept in which declared governance and readiness conditions frame bounded work; the term does not itself specify runtime mechanics. |
| **Self Engineering** | The established strategic direction in which Forge turns its repository-held model into separately governed capabilities while retaining human approval and evidence-first assessment. |
| **Self Hosting** | An unresolved term, not an established Forge phase, capability, runtime commitment, or architectural definition. |
| **Renderer Host** | An unresolved term discussed with future Studio possibilities; bootstrap establishes no renderer, UI implementation, or host model. |
| **Mission Runtime** | A future Capability boundary for a runtime that could coordinate bounded engineering work; bootstrap establishes neither its behavior nor implementation. |
| **Capability Qualification** | Capability-specific assessment of declared criteria and evidence. It establishes evidence, not self-approval or production status. |
| **Architecture Steward** | A future conceptual responsibility for coherent Architecture Handbook evolution and reconciliation; bootstrap establishes no role implementation or authority mechanism. |

## Terminology boundary

Terms labelled future or unresolved preserve bootstrap knowledge without
claiming implementation, roadmap selection, or approval. Their possible
evolution remains subject to a separately authorized Engineering Intent and
evidence-backed Capability work.
