# Forge Open Questions and Deferred Decisions

## Purpose and authority

This chapter records only unresolved topics already discussed during bootstrap.
It preserves their boundaries without inventing answers, selecting roadmap
work, or authorizing implementation.

## Open questions

| Topic | Open question |
| --- | --- |
| Runtime API | What stable interface should let Runtime Providers derive provider-specific Runtime Prompts from approved Engineering Intent while keeping intent canonical? |
| Capability Marketplace | How could future capability discovery and composition work without implying installation, distribution, approval, or compatibility? |
| Cloud deployment | Whether Forge needs a cloud product or deployment model, while preserving its local-first foundation and repository-first evidence. |
| Execution Host abstraction | What contracts permit replaceable Execution Hosts to execute bounded work without owning knowledge, governance, or completion decisions? |
| Knowledge Distillation implementation | How can candidates be identified with provenance and uncertainty while retaining human review and no automatic authority transfer? |
| Architecture Handbook authoring | How should reconciled Repository Knowledge become a maintained Architecture Handbook without making bootstrap material or conversations authoritative? |
| Self Engineering strategy | Which bounded, governed capabilities should mature the completed Foundation toward Self Engineering without self-authorization? |
| Large-scale multi-user governance | Which profiles, roles, and approval boundaries are needed beyond bootstrap's local governance model? |
| Capability distribution | How, if at all, capabilities can become distributable while retaining explicit dependencies, qualification, and governance. |
| Future Runtime Providers | Which providers Forge should support and how their translation behavior can remain replaceable and derived from canonical intent. |

## Deferred decisions

| Decision | Why deferred |
| --- | --- |
| Marketplace implementation | Bootstrap establishes only a future discoverability and composition direction. It does not establish marketplace behavior, installation mechanics, or distribution policy. |
| Cloud strategy | The completed foundation is local-first and does not establish a cloud product, service, or runtime. A cloud choice needs separately reconciled architecture and governance. |
| Native Runtime | Forge does not yet own a Runtime Provider, Forge Runtime, Mission Runtime, or independent Execution Host. Selecting one would exceed bootstrap capture. |
| Commercial capability distribution | Capability declaration, qualification, and possible distribution are distinct. No commercial model or distribution mechanism was established during bootstrap. |
| Advanced multi-user governance | Bootstrap preserves human governance but establishes no multi-user roles, access control, or workflow mechanics. Those decisions require a future governance capability. |
| Future UI implementations | No Studio, renderer, SaaS interface, or Renderer Host was established. A future UI must not redefine Workspace ownership, canonical knowledge, or governance. |

## Decision rule

Each topic remains open or deferred until a separately authorized Engineering
Intent reconciles it with the Bootstrap Knowledge Package, repository evidence,
human governance, and qualification evidence. Open questions do not imply a
backlog item or execution authority.
