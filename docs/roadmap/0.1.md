# Forge Roadmap

## Bootstrap Phase A — Complete

Bootstrap Phase A is complete. It delivered the local deterministic foundation from increments 0.1 through 0.8 and subsequent loader/proposal-generator/prompt-artifact repairs.

## Phase B — Self Engineering

The next phase is Self Engineering. Each increment remains a separately governed bounded objective. Engineering Platform remains the replaceable Execution Host; Forge core does not acquire a second execution engine.

## Dual Engineering Learning System

Forge's target architecture contains two complementary loops over Engineering Action evidence:

- **Quality Learning** improves how a specific project is engineered through governed evolution of DoR/DoD, guards, tests, Goldens, validation, repository governance and Human Gates.
- **Knowledge Learning** extracts reusable engineering observations and routes them through the independent AI Platform Engineering Knowledge Base lifecycle toward governed Certified Knowledge.

The canonical architecture is in `docs/architecture/dual-engineering-learning-system.md`, with quality semantics in `engineering-quality-learning-loop.md` and clean-install/bootstrap semantics in `self-contained-engineering-contract-bootstrap.md`.

## Planned implementation sequence

### L0 — Engineering Contract Foundation (EP prerequisite)

**Owner:** Engineering Platform.  
**Timing:** immediately after P-TRANSPORT.

Deliver first-class capability classification, Effective DoR, pre-dispatch readiness, Effective DoD, proof requirements, Human Gates, live/historical workflow projection, completion enforcement, structured `ActionQualityOutcome`, packaged baseline contracts and immutable Action contract snapshots.

**Exit:** EP can explain and enforce why an Action is Ready and what evidence is required for Done without source-repository access.

### L1 — Learning Evidence + New-Project Bootstrap Contract

**Owner:** Forge + EP contract boundary.

Define the versioned Action learning-evidence envelope and the self-contained new-project bootstrap contract: installed baseline provenance, project-owned engineering contract creation, baseline/project/Action versioning, inclusion/redaction/privacy/retention and clean-install behavior.

**Exit:** a clean installation can create a project-owned engineering contract and terminal Actions can be observed without coupling Forge to EP storage or pcvantol/source repositories.

### L1-R — Managed Repository Governance Baseline

**Owner:** Forge, with repository-host adapters and EP/CI proof integration.  
**Timing:** immediately after L1 and before Installer/Release qualification; implement early enough that later Forge-created projects use it by default.

First inventory mature Forge/EP/TDE/AI-development-contract repositories and classify observed repository settings into generic best practice, capability-dependent policy, organization/project-specific policy, workflow-required policy and historical/incidental settings. Do not blindly copy pcvantol settings.

Define a versioned generic GitHub Managed baseline (`MANAGED_GITHUB_BASELINE_V1` or equivalent) covering where applicable:

- default/protected branch policy;
- PR requirement and review semantics;
- conversation resolution;
- required checks derived from validation/capability profiles;
- security/CodeQL policy;
- Trusted Delivery / owner-authorization integration where applicable;
- CODEOWNERS/ownership policy;
- merge strategy and branch cleanup;
- workflow permissions/security;
- dependency-update policy;
- ruleset/branch-protection desired state;
- repository-host capability limitations.

Implement declarative Repository Desired State, GitHub provisioning, idempotent reconciliation, read-back qualification and bounded evidence. A successful mutation call is insufficient: actual host state must be compared with expected state.

Add existing-repository adoption/drift semantics. Forge must inspect and propose reconciliation rather than silently overwriting intentional policy.

Required target:

`REPOSITORY_GOVERNANCE = PASS`

for a newly created Managed repository before it becomes generally Ready.

**Exit:** `New Project -> Managed -> GitHub` creates/attaches the repository, installs bootstrap/CI/security assets, applies the qualified generic governance baseline, reads back the host state and proves compliance without consulting development/source-authority repositories.

### L2 — Quality Observer v1

**Owner:** Forge.

Run lightweight analysis after every Action. Persist traceable signals for DoR misses, DoD escapes, late failures, human rejection, repeated repair, security findings, documented-only requirements, repeated manual checks and repository-governance escapes. Zero automatic governance mutation.

### L3 — Quality Learning Review + Hardening Proposals

**Owner:** Forge.

Implement N-Action/milestone reviews, `defect -> root cause -> pattern -> systemic hardening`, requirement-to-enforcement audits, `QualityLearningRecord`, repeated-defect detection and regression/mutation proof proposals. Proposals may ADD/STRENGTHEN/MERGE/RELAX/RETIRE controls, including repository-governance controls.

### L4 — Workspace Quality Governance

**Owner:** Workspace.

Visualize DoR/DoD/Human Gates, repository-governance status/drift and Quality Learning Reviews. Provide governed Accept/Modify/Reject and Managed hardening Actions.

### L5 — Knowledge Evidence Export Contract

**Owner:** Forge + EP + KB boundary.

Define the approved redacted path from Action/source evidence to KB Engineering Observations, preserving source identity, commit/version anchors, evidence-vs-interpretation separation and read-only source semantics. No KB server/API required.

### L6 — Knowledge Observer v1

**Owner:** Forge with KB authority preserved.

Run lightweight post-Action extraction analysis and propose observations, reusable implications, candidate links, classifications, relationships, duplicates, confidence and uncertainty. Never certify/promote knowledge.

### L7 — Workspace Knowledge Governance

**Owner:** Workspace + KB governance integration.

Present observation/candidate proposals, source lineage, uncertainty, relationships and KB lifecycle state and allow governed review actions.

### L8 — Certified Knowledge Consumption in Forge

**Owner:** Forge + KB read-only consumer contract.

Consume Certified Knowledge in planning with lineage/rationale. KB remains additive and Certified Knowledge is not automatic project policy.

### L9 — Continuous Dual Learning Automation

**Owner:** Forge orchestration; Workspace governance; KB independent authority.

Run Quality/Knowledge observers after Actions, milestone/release reviews, repeated-defect escalation, source/drift/gap triggers and bounded health/backlog projections. Automation proposes/prepares; it does not self-approve.

### L10 — Learning Effectiveness + Distribution Qualification

**Owner:** Forge + EP/CI + Installer/Release qualification.

Measure first-pass qualification, DoR misses, DoD escapes, human-review escape rate, repeated defects and time-to-Done. Use negative/mutation qualification to prove historical defects are caught. Qualify stale/redundant control retirement.

Make the permanent clean-install qualification explicit:

- no access to pcvantol/development source-authority repositories;
- released Forge/EP/Workspace installed on a clean machine;
- local baseline contracts available;
- new project contract created;
- Managed GitHub repository desired state provisioned and read back;
- `REPOSITORY_GOVERNANCE = PASS`;
- DoR/DoD/Human Gates enforced;
- no source-repository runtime dependency.

The baseline-availability portion is air-gapped. Repository-host provisioning uses only the selected user's repository-host credentials/connectivity, never pcvantol/source-authority access.

## Dependency and scheduling guidance

```text
P-TRANSPORT complete
  -> L0 Engineering Contract Foundation
  -> L1 New-Project Bootstrap Contract
  -> L1-R Managed Repository Governance Baseline
  -> remaining EP standalone / Installer / Release qualification

Forge runtime/planning maturity
  -> L2 -> L3 -> L4

KB integration readiness
  -> L5 -> L6 -> L7 -> L8

L2 + L6 stable
  -> L9 -> L10
```

L0/L1/L1-R happen early because they improve every later project and ensure Installer/Release qualify the real self-contained Managed-project model. L5-L8 never block standalone engineering execution.

## Product milestones

1. **Executable Managed Engineering Contract** — L0 + L1 + L1-R: explicit Ready/Done semantics, portable evidence, clean project bootstrap and qualified repository governance.
2. **Project Quality Learner** — L2-L4.
3. **Reusable Knowledge Learner** — L5-L8.
4. **Continuous Learning Platform** — L9-L10.

## Non-goals and authority constraints

Forge does not become a second execution engine. EP does not autonomously rewrite project policy. Forge/EP/Workspace do not certify reusable knowledge. KB does not mutate source repositories or become an execution dependency. Product upgrades do not silently rewrite project/repository policy. Generic Managed repository governance is not a copy of pcvantol repository settings; it is a separately qualified versioned product baseline.
