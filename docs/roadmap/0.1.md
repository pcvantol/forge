# Forge Roadmap

## Bootstrap Phase A — Complete

Bootstrap Phase A is complete. It delivered the local, deterministic
foundation from increments 0.1 through 0.8 and the subsequent loader,
proposal-generator, and prompt-artifact repairs. The closure record is
[Bootstrap Milestone A Report](../reports/bootstrap-milestone-a.md).

## Phase B — Self Engineering

The next phase is **Self Engineering**, beginning with **Forge Phase B —
Increment 1.0**. It is a planned transition, not an implemented capability.
Each increment remains subject to a separate bounded objective and human
approval.

### Canonical runtime evolution

The canonical implementation strategy is CLI-first. The deterministic Forge
CLI is the first executable runtime; the Forge Runtime Service evolves later
from the qualified CLI and automates its existing behavior without creating a
second execution engine. The complete implementation sequence, ownership
boundaries, bootstrap adapter rule, autonomous-engineering boundary, and
Portfolio relationship are defined in the
[Runtime Evolution Roadmap](../architecture/runtime-evolution-roadmap.md).

Engineering Platform 1.5 remains the temporary reference Execution Host behind
the Execution Host Contract and Bootstrap Execution Host Adapter. Forge core
has no direct Engineering Platform integration.

### Engineering quality learning target

Forge's target architecture includes a generic **Engineering Quality Learning
Loop**. Engineering Platform first provides enforceable per-Action Effective
Definition of Ready, Effective Definition of Done, proof requirements, Human
Gates, workflow projection, and structured quality outcomes. Forge then
observes completed Engineering Actions, clusters defects into root causes and
systemic patterns, audits requirement-to-enforcement gaps, and proposes
hardening of the project's executable engineering contract. Workspace is the
human governance surface for accepting, modifying, or rejecting those
proposals.

The Quality Observer is intended to run after every Engineering Action without
silently changing policy. Heavier reviews can be requested over recent Actions
or triggered by milestones, human-review rejection, repeated defects, security
findings, or abnormal repair/qualification patterns. Accepted hardening is
stored in the canonical project contract and enforced by EP/CI on future work.

The complete target, including Effective DoR/DoD, Human Gates, workflow
projection, Quality Learning Records, regression proof, and the staged
EP → Forge → Workspace ownership model is defined in
[Engineering Quality Learning Loop](../architecture/engineering-quality-learning-loop.md).

This is a planned target architecture, not a claim that the learning capability
is currently implemented.

### Delivered after the intended sequence

Phase B — Increment 2.1 establishes the Execution Host Contract as the
replaceable execution boundary. Engineering Platform 1.5 remains its reference
implementation; a later increment may document that reference without copying
or generalizing its implementation.

No Phase B item implements a Runtime Service, Studio, repository operation, or
new engineering behavior without a separately authorized increment.
