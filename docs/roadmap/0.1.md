# Forge Roadmap

## Bootstrap Phase A — Complete

Bootstrap Phase A is complete. It delivered the local, deterministic
foundation from increments 0.1 through 0.8 and the subsequent loader,
proposal-generator, and prompt-artifact repairs. The closure record is
[Bootstrap Milestone A Report](../reports/bootstrap-milestone-a.md).

## Phase B — Self Engineering

The next phase is **Self Engineering**. Each increment remains subject to a
separate bounded objective and human approval.

### Canonical runtime evolution

The canonical implementation strategy is CLI-first. The deterministic Forge
CLI is the first executable runtime; the Forge Runtime Service evolves later
from the qualified CLI and automates its existing behavior without creating a
second execution engine. The complete implementation sequence, ownership
boundaries, bootstrap adapter rule, autonomous-engineering boundary, and
Portfolio relationship are defined in the
[Runtime Evolution Roadmap](../architecture/runtime-evolution-roadmap.md).

Engineering Platform remains the replaceable Execution Host behind the
Execution Host Contract. Forge core must not acquire a second execution engine.

## Dual Engineering Learning System — target architecture

Forge's target architecture contains two complementary loops over Engineering
Action evidence:

- **Quality Learning** improves how a specific project is engineered by
  proposing executable changes to Effective DoR/DoD, guards, tests, Goldens,
  validation and Human Gates.
- **Knowledge Learning** extracts reusable engineering observations and routes
  them through the independent AI Platform Engineering Knowledge Base (KB)
  lifecycle toward governed Certified Knowledge.

Both observers may run after every Engineering Action, but neither silently
changes authority. Project-specific hardening belongs to the project contract;
reusable knowledge belongs to the KB lifecycle. Workspace is the human
governance surface. EP enforces the current Action contract and produces
evidence.

The canonical product architecture is [Dual Engineering Learning System](../architecture/dual-engineering-learning-system.md).
Quality-specific semantics are detailed in [Engineering Quality Learning Loop](../architecture/engineering-quality-learning-loop.md).
The KB repository remains canonical for its own extraction, ingestion,
generalization and certification lifecycle.

## Planned implementation sequence

The sequence below separates prerequisites from learning intelligence so value
arrives early without making EP execution dependent on Forge or the KB.

### L0 — Engineering Contract Foundation (EP prerequisite)

**Owner:** Engineering Platform.  
**Timing:** immediately after P-TRANSPORT, before P-NEUTRAL/Installer work.

Deliver first-class per-Action:

- capability classification;
- Effective Definition of Ready;
- pre-dispatch readiness gate;
- Effective Definition of Done;
- proof requirements;
- Human Gates;
- live and historical Action workflow projection;
- completion enforcement;
- structured `ActionQualityOutcome` evidence.

This increment provides immediate value independently of Forge learning.

**Exit:** EP can explain why an Action was Ready, what Done requires, which
proof is pending, and why completion is or is not permitted.

### L1 — Learning Evidence Contract

**Owner:** Forge + EP contract boundary.

Define a stable, bounded, versioned Engineering Action learning-evidence
envelope. Include Action identity, intent, capability profile, DoR/DoD proof,
validation/security/human-review outcomes, repair cycles, architecture decision
references, delivery evidence and source commit anchors.

Define inclusion/exclusion, secret redaction, privacy and retention semantics.
Forge consumes evidence; it does not read arbitrary EP internals.

**Exit:** completed/terminal Actions can be observed without coupling Forge to
EP storage implementation.

### L2 — Quality Observer v1

**Owner:** Forge.

Run lightweight analysis after every Engineering Action. Persist learning
signals and Quality Outcome references without changing policy. Detect DoR
misses, DoD escapes, late failures, human-review rejection, repeated repair,
security findings, documented-only requirements and repeated manual checks.

**Exit:** every eligible Action can produce a traceable quality-learning signal
set; zero automatic governance mutation.

### L3 — Quality Learning Review + Hardening Proposals

**Owner:** Forge.

Implement on-demand and threshold/milestone reviews over N Actions. Cluster:

`defect -> root cause -> pattern -> systemic hardening`.

Add requirement-to-enforcement audit, hardening proposal types, regression/
mutation proof proposals, repeated-defect detection and `QualityLearningRecord`.

**Exit:** Forge can propose `ADD/STRENGTHEN/MERGE/RELAX/RETIRE` changes with
traceable evidence and expected enforcement impact.

### L4 — Workspace Quality Governance

**Owner:** Workspace.

Visualize Action DoR/DoD/Human Gates and Quality Learning Reviews. Provide
`Accept / Modify / Reject` for hardening proposals and create governed Managed
Actions for accepted project-contract changes.

**Exit:** no quality-learning proposal can silently change project policy;
accepted hardening is visible, auditable and executable.

### L5 — Knowledge Evidence Export Contract

**Owner:** Forge + EP + KB boundary.

Define the approved path from Engineering Action/source evidence to KB
Engineering Observations. Preserve source identity, commit/version anchors,
evidence-vs-interpretation separation, extraction policy and read-only source
semantics. Define explicit EP evidence export rather than KB access to EP
internal storage.

This stage does not require a KB server/API.

**Exit:** an Action can produce a governed, redacted observation/export package
that the KB can ingest without source mutation or self-certification.

### L6 — Knowledge Observer v1

**Owner:** Forge, with KB lifecycle authority preserved.

Run lightweight post-Action extraction analysis. Propose Engineering
Observations, reusable implications, candidate links, classifications,
relationships, duplicates, confidence and uncertainty. Do not certify or
promote knowledge.

Initially integrate through explicit CLI/Git-backed KB workflows if that is the
qualified KB interface.

**Exit:** eligible Actions can create traceable knowledge-learning proposals
without making KB availability an execution dependency.

### L7 — Workspace Knowledge Governance

**Owner:** Workspace + KB governance integration.

Present proposed observations/candidates, source lineage, uncertainty,
duplicate/relationship suggestions and KB lifecycle status. Allow authorized
operators to initiate governed KB review/promotion actions without Workspace
becoming knowledge authority.

**Exit:** knowledge-learning proposals have a usable human governance loop.

### L8 — Certified Knowledge Consumption in Forge

**Owner:** Forge + KB read-only consumer contract.

Add a replaceable read-only adapter for Certified Knowledge. Use Certified
Knowledge in Mission/architecture planning with lineage and rationale. KB
availability remains additive: planning/execution must have an explicit
bounded behavior when knowledge is unavailable.

Certified Knowledge is not automatic project policy; project adoption remains
governed.

**Exit:** Forge can explain which Certified Knowledge influenced a plan and
preserve its lineage/version.

### L9 — Continuous Dual Learning Automation

**Owner:** Forge orchestration; Workspace governance; KB independent authority.

Add background/event-driven operation:

- Quality Observer after each Action;
- Knowledge Observer after each Action;
- milestone/release Quality Reviews;
- repeated-defect escalation;
- repository/source change observation triggers;
- knowledge drift/gap signals;
- backlog/health projections;
- scheduled consolidation where justified.

Automation proposes and prepares; it never self-approves project governance or
KB certification.

**Exit:** the dual loop operates continuously with bounded cost, traceability,
health monitoring and human-governed authority transitions.

### L10 — Learning Effectiveness and Self-Hardening Qualification

**Owner:** Forge + project CI/EP proof mechanisms.

Measure whether accepted learning actually prevents recurrence. Track first-
pass qualification, DoR misses, DoD escapes, human-review escape rate, repeated
defect rate and time-to-Done. Use negative/mutation qualification where
practical to prove historical defects are now caught.

Review stale/redundant controls and allow governed proposals to relax or retire
them. Learning must improve signal, not only accumulate rules.

**Exit:** the platform can demonstrate that accepted hardening changes future
engineering outcomes and can detect when its learning controls are ineffective.

## Dependency and scheduling guidance

The implementation order is intentionally asymmetric:

```text
P-TRANSPORT complete
  -> L0 Engineering Contract Foundation
  -> remaining EP standalone milestones (P-NEUTRAL / Installer / Release)

Forge runtime/planning maturity
  -> L1 -> L2 -> L3
  -> L4 when Workspace review UX is available

KB integration readiness
  -> L5 -> L6 -> L7
  -> L8 Certified Knowledge consumption

L2 + L6 stable
  -> L9 continuous dual automation
  -> L10 effectiveness/self-hardening qualification
```

L0 should happen early because it immediately improves every later Engineering
Action. L5-L8 must not block standalone EP or Forge operation. Knowledge
integration is additive by architecture.

## Product milestones

For planning, the increments roll up into four product milestones:

1. **Executable Engineering Contract** — L0-L1: Actions have explicit Ready/Done
   semantics and portable learning evidence.
2. **Project Quality Learner** — L2-L4: Forge learns how each project should be
   engineered and Workspace governs hardening.
3. **Reusable Knowledge Learner** — L5-L8: engineering evidence flows through
   the KB lifecycle and Certified Knowledge returns to Forge planning.
4. **Continuous Learning Platform** — L9-L10: both loops operate continuously
   and their effectiveness is measured.

## Non-goals and authority constraints

- Forge does not become a second execution engine.
- EP does not autonomously rewrite project policy.
- Forge/EP/Workspace do not certify reusable engineering knowledge.
- The KB does not mutate registered source repositories.
- The KB does not become an implicit EP admission/execution dependency.
- Project-specific quality controls are not automatically Certified Knowledge.
- Certified Knowledge is not automatically project policy.
- A KB server/daemon is not required unless later productization evidence
  justifies it.

## Delivered after the intended sequence

Phase B — Increment 2.1 establishes the Execution Host Contract as the
replaceable execution boundary. Engineering Platform remains its reference
implementation until a separately governed evolution changes that boundary.

No Phase B item implements a Runtime Service, Studio, repository operation, or
new engineering behavior without a separately authorized increment.
